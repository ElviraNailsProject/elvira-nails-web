# elvira-nails-web

Веб-сайт и платформа бронирования для Эльвиры — мастера ногтевого сервиса и преподавателя в Нидерландах.

Проект создаётся как реальный коммерческий продукт и одновременно используется как совместный проект для портфолио. Репозиторий может быть публичным, поэтому в него **никогда не должны попадать реальные данные клиентов и учеников, секреты, пароли и другая конфиденциальная информация**.

## Технологический стек

- **Next.js 16 + TypeScript** — основа приложения: публичная часть сайта, административная панель, серверная логика и маршрутизация.
- **Tailwind CSS** — стилизация интерфейса и адаптивная вёрстка.
- **ESLint + Prettier** — проверка качества кода и единое форматирование.
- **PostgreSQL** — основная реляционная база данных для записей, услуг, учеников, акций и других структурированных данных.
- **Supabase** — облачная инфраструктура для PostgreSQL, аутентификации и хранения файлов.
- **Prisma ORM 7** — типизированная работа с базой данных, описание схемы и управление миграциями.
- **React Hook Form** — работа с формами и их состоянием.
- **Zod** — проверка и валидация данных, поступающих из форм и серверных запросов.
- **TanStack Query** — управление серверными данными в административной части: кэширование, повторные запросы и мутации.
- **date-fns** — работа с датами и временем, необходимая для бронирования и календаря.
- **Vercel** — размещение приложения и создание preview-окружений.
- **GitHub Actions** — автоматическая проверка кода, типов и production-сборки.

## Архитектура

Проект придерживается простого разделения ответственности:

`Next.js → бизнес-логика → Prisma → PostgreSQL`

Supabase используется как облачная инфраструктура для базы данных, аутентификации и хранения изображений и файлов.

Публичная часть сайта и административная панель работают в рамках одного Next.js-приложения, но имеют разные уровни доступа и требования к безопасности.

**Бизнес-логика не должна находиться непосредственно внутри UI-компонентов.** Компоненты отвечают за интерфейс, а работа с данными и правила бизнеса должны находиться в соответствующих слоях приложения.

## Окружения

Development и production должны быть полностью разделены.

### Development

Используются:

- тестовые или mock-данные;
- отдельный development-проект Supabase;
- preview-деплои Vercel.

### Production

Используются:

- реальные данные бизнеса;
- отдельный production-проект Supabase;
- production-деплой в Vercel.

Секреты и переменные окружения хранятся только локально или в защищённом хранилище секретов хостинг-провайдера. **Они никогда не коммитятся в Git.**

## Локальная разработка

### Требования

- **Node.js 24 LTS**
- **npm**

Node.js 24 LTS является рекомендуемой версией для проекта. Next.js 16 требует Node.js версии 20.9 или выше.

## Git workflow

Работа ведётся через feature-ветки. Прямые коммиты в `main` не используются.

Пример:

```text
main
└── feature/<краткое-описание>
```

Типичный процесс:

1. Создать feature-ветку.
2. Реализовать изменения.
3. Проверить проект локально.
4. Создать Pull Request.
5. Дождаться успешного прохождения CI.
6. Провести code review.
7. Объединить изменения с `main`.

## Безопасность публичного репозитория

Репозиторий может оставаться публичным для использования в портфолио. Поэтому перед каждым коммитом необходимо проверять, что в изменения не попали секреты или реальные персональные и бизнес-данные.

**Никогда не коммитьте:**

- `.env.local` и другие файлы с секретами;
- пароли от базы данных;
- приватные API-ключи;
- Supabase service-role key и другие секретные ключи;
- реальные персональные данные клиентов и учеников;
- приватные production-экспорты;
- дампы базы данных с реальными данными;
- другую конфиденциальную информацию бизнеса.

## Передача проекта в production

Проект должен оставаться независимым от конкретного окружения, чтобы его можно было без существенных изменений перенести из development в production.

Для полноценного production-запуска потребуется:

- приватный репозиторий или передача существующего репозитория владельцу проекта;
- production-проект Supabase;
- production-переменные окружения;
- production-конфигурация Vercel;
- реальные данные и файлы клиента.

При этом исходный код приложения не должен содержать привязок к конкретным секретам, аккаунтам или данным development-окружения.
