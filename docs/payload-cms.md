# Payload CMS: настройка и запуск

CMS работает внутри Next.js по `/admin`, REST API — по `/api/cms`. Используются Payload 3.91, штатные формы, авторизация и версии документов. GraphQL отключён. Общая верхняя навигация и тема добавлены через публичные точки расширения Payload, без изменения файлов библиотеки.

## Две независимые базы

| Переменная         | Владелец схемы | Назначение                                                 |
| ------------------ | -------------- | ---------------------------------------------------------- |
| `DATABASE_URL`     | Prisma         | Работа существующего приложения с услугами и бронированием |
| `DIRECT_URL`       | Prisma         | Миграции существующего приложения                          |
| `CMS_DATABASE_URL` | Payload        | Отдельная база кейсов, медиа, администраторов и заявок CMS |

Не указывайте существующую Prisma-базу в `CMS_DATABASE_URL`. Конфигурация отклоняет очевидное совпадение адреса, порта и имени БД; разные aliases/pooler-адреса одной базы могут обойти такую проверку, поэтому отдельная база должна быть создана фактически. `push: false` отключает автоматическое изменение схемы при запуске, `disableCreateDatabase: true` требует создать БД заранее.

В [compose.yaml](../compose.yaml) два независимых сервиса PostgreSQL 17:

- `postgres`: база приложения `elvira_dev`, порт `127.0.0.1:54322`.
- `cms-postgres`: база CMS `elvira_cms_dev`, порт `127.0.0.1:54323`.

Контейнеры имеют отдельные volumes. Пароли в Compose предназначены только для этого локального окружения. Если база приложения уже настроена, достаточно `docker compose up -d cms-postgres`.

## Переменные окружения

Используйте [.env.example](../.env.example) как справочник. Существующий `.env` с `DATABASE_URL` и `DIRECT_URL` сохраняется. Переменные CMS можно добавить в `.env.local`:

```dotenv
CMS_DATABASE_URL="postgresql://elvira_cms_dev:local_cms_dev_only@127.0.0.1:54323/elvira_cms_dev"
PAYLOAD_SECRET=""
APP_ORIGIN="http://localhost:3000"
CMS_STORAGE="local"
```

`PAYLOAD_SECRET` должен содержать случайное значение длиной не менее 32 символов. Создайте его локально и вставьте в свой файл окружения:

```sh
node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"
```

Не используйте значение из примера в качестве секрета. `APP_ORIGIN` должен совпадать с адресом в браузере, включая схему и порт: `localhost` и `127.0.0.1` — разные origins. Для запуска на 3100 задайте соответствующий origin и используйте `npm run dev -- --port 3100`.

Next.js и команды `cms:*` читают `.env.local` и `.env`. Prisma CLI в текущей конфигурации загружает `.env` и переменные процесса; он не подхватывает `.env.local` через обёртку CMS.

## Первый запуск и владелец

```sh
npm ci
docker compose up -d
npm run db:generate
npm run cms:types
npm run cms:importmap
npm run cms:migrate
```

Для уже настроенной Prisma-базы повторно применять её миграции не требуется. Для нового локального окружения отдельно настройте Prisma по `prisma/schema.prisma` и миграциям проекта; команда `npm run db:migrate` относится только к `DIRECT_URL`.

Первого администратора создаёт закрытый CLI-сценарий. Временно задайте в окружении терминала или игнорируемом `.env.local`:

```dotenv
CMS_ADMIN_EMAIL="owner@example.test"
CMS_ADMIN_PASSWORD=""
CMS_ADMIN_NAME="Владелец"
```

Укажите собственный пароль не короче 16 символов, затем выполните:

```sh
npm run cms:admin
npm run dev
```

Войдите на `/admin/login`. Скрипт отказывается создавать первого владельца, если администратор уже существует. После создания удалите bootstrap-пароль из файла окружения. Публичной регистрации нет: также закрыт штатный endpoint первоначальной регистрации Payload. Дополнительные аккаунты создаёт уже авторизованный администратор в коллекции «Администраторы».

CMS использует собственную сессию, а не старые dev-пароли или Supabase Auth allowlist. Срок токена — 2 часа, после 5 неудачных попыток вход блокируется на 15 минут. Cookie использует `SameSite=Strict` и `Secure` в production. Доступ к административным коллекциям проверяется на сервере; скрытая ссылка в навигации не является защитой.

## Что видит администратор

Верхнее меню ведёт к кейсам учениц, заявкам на обучение, медиатеке и настройкам аккаунта. Имя в шапке берётся из текущей учётной записи. В аккаунте можно выбрать язык интерфейса; язык контента выбирается штатным переключателем локали CMS.

Контент кейсов поддерживает NL / EN / RU / **UK**. В кейсах и заявках на обучение доступны ровно три статуса: «Учится», «В ожидании», «Закончила». Публикация кейса управляется отдельно штатными действиями Payload.

Коллекция `training-applications` содержит записи, внесённые владельцем вручную. Публичная страница `/book-appointment` пока остаётся заглушкой: формы отправки заявки в этом модуле нет. Приём заявок с сайта, перенос Prisma-заявок, записи на процедуры и остальные разделы бронирования требуют отдельной интеграции.

## Изображения и production

При `CMS_STORAGE=local` файлы сохраняются в `.local/cms-media`, вне публичной директории Next.js. Это подходит для разработки и серверов с постоянным диском. Для serverless используйте приватное S3-совместимое хранилище:

```dotenv
CMS_STORAGE="s3"
CMS_S3_BUCKET="your-private-bucket"
CMS_S3_REGION="your-provider-region"
CMS_S3_ENDPOINT=""
CMS_S3_ACCESS_KEY_ID=""
CMS_S3_SECRET_ACCESS_KEY=""
CMS_S3_FORCE_PATH_STYLE="false"
```

Для AWS S3 `CMS_S3_ENDPOINT` обычно остаётся пустым; для совместимого провайдера укажите его endpoint и настройки региона/path style. Bucket и объекты должны оставаться **private**. Приложение не настраивает IAM и bucket policy за вас. Дайте серверной учётной записи необходимые права только на выбранный bucket и храните ключи на сервере, без префикса `NEXT_PUBLIC_`.

Файлы выдаются через Payload с проверкой публикации кейса. Не включайте `disablePayloadAccessControl` и не заменяйте адреса на публичные bucket URL. Для фото и thumbnail устанавливается `Cache-Control: private, no-store`, чтобы снятие с публикации закрывало последующие запросы. Ограничения загрузки и модели доступа подробно описаны в [документации кейсов](student-cases.md).

Для production задайте отдельные базы, постоянный `PAYLOAD_SECRET`, точный HTTPS `APP_ORIGIN`, private S3 и секреты хостинга. Запускайте миграции CMS отдельным шагом релиза до старта обновлённого приложения. Сборка `npm run build` сама не применяет миграции и не создаёт владельца. Не запускайте production с локальным ephemeral storage.

Резервное копирование баз и файлов, мониторинг и периодическая очистка неиспользуемых медиа настраиваются отдельно. Для восстановления пароля в production обязательно настройте SMTP по инструкции ниже.

## Почта и восстановление пароля

Адаптер `src/cms/email.ts` использует официальный `@payloadcms/email-nodemailer` версии 3.91. Настройте SMTP-провайдера и добавьте серверные переменные окружения:

```dotenv
CMS_SMTP_HOST="smtp.your-provider.example"
CMS_SMTP_USER=""
CMS_SMTP_PASSWORD=""
CMS_SMTP_FROM="noreply@your-domain.example"
CMS_SMTP_FROM_NAME="Elvira"
```

Обязательны host, user, password и from. `CMS_SMTP_FROM` — подтверждённый провайдером адрес отправителя; отображаемое имя задаётся отдельно в `CMS_SMTP_FROM_NAME`. Соединение использует порт 587 с обязательным STARTTLS. Для такого подключения настройте SMTP submission у выбранного провайдера; это не режим прямого TLS на порту 465.

SMTP не проверяется сетевым запросом при загрузке конфигурации или сборке (`skipVerify: true`). Это позволяет собирать приложение без отправки писем, но не подтверждает доставку: после настройки проверьте восстановление на принадлежащем вам тестовом адресе.

Если обязательные настройки отсутствуют, восстановление по почте недоступно и адаптер возвращает понятную ошибку 503. Такое поведение одинаково в development и production: случайный тестовый почтовый ящик не создаётся, письмо и ссылка с токеном не выводятся в консоль. Подключение SMTP и реальные почтовые доставки не выполняются автоматически установкой пакета.

## Изменение схемы

Конфигурации коллекций находятся в `src/cms/collections`, миграции — в `src/cms/migrations`. После изменения полей:

```sh
npm run cms:types
npm run cms:importmap
npm run cms -- migrate:create
```

Проверьте сгенерированную миграцию, примените её к development-базе командой `npm run cms:migrate`, проверьте сценарий и коммитьте миграцию вместе с конфигурацией. Миграции Payload не применяются командами Prisma. Существующие Prisma-кейсы автоматически не импортируются.

## Проверки

```sh
npm test
npm run types
npm run lint
npm run build
```

Эти команды описывают процедуру проверки, а не подтверждают прохождение проверок на вашей машине. Для build также должны быть доступны необходимые переменные окружения.

HTTP-интеграционный сценарий запускается против отдельного локального тестового сервера и отдельной тестовой CMS-базы. Создайте синтетического владельца через `cms:admin`, запустите приложение с тестовой конфигурацией и задайте `TEST_BASE_URL`, `TEST_ADMIN_EMAIL`, `TEST_ADMIN_PASSWORD` в окружении процесса:

```sh
npm run test:integration
```

Если удобнее передать тестовые параметры из файла, создайте игнорируемый `.env.test.local`, содержащий только эти три переменные, и выполните переносимую команду Node.js 24:

```sh
node --env-file=.env.test.local scripts/test-cms.mjs
```

Сценарий принимает только loopback origin, создаёт синтетические кейс, фотографии и заявку, проверяет ограничения доступа, языки, публикацию, закрытые контакты, медиа и три статуса. Он пытается удалить созданные записи и файлы после проверки; при ошибке очистки сообщает оставшиеся ID. Локальный адрес сам по себе не гарантирует тестовую базу: убедитесь, что работающий сервер подключён именно к одноразовому тестовому окружению.
